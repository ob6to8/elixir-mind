# Journal — 2026-07-31

The more I work with agents in this system — meaning, the more I develop this
repo with coding agents — the more I come to the conclusion that it's not
possible to truly audit agent behavior without a complete understanding of what
the agent is doing. This means not only understanding the domain that it's
working in — in this case, the knowledge that it's committing to the repo, as
well as the epistemological map it's creating across it — but also,
development-wise, the way it's creating what it's creating. Specifically, an
understanding of the code and the architected system itself down to the
foundation. This, if correct, cuts against the core hope for agents. The hope is
that you can offload cognitive responsibility for certain tasks of work so that
you can rise to a higher abstraction level and leverage effort. This also would
cut against assumptions in the industry. (Although it started to seem as if
those assumptions are being heavily questioned in the industry.) I know for me,
I have strived to walk a middle ground of understanding what this repo is and
how it's developed from a high level while seeking to drop down to lower-level
understanding where necessary. I've hoped that my aspirationally quick but deep
surveying of agent work would give me enough of a mental model to dictate
further work in a way where both cognitive and technical debt are not
accumulated. I now think that the level I've been working at has not allowed for
this. I feel pretty close to seeing this repo being at the same level of
"complexity escape" — if I could coin a phrase — that I encountered with my
previous attempt. The difference being I have been more intentional this time,
and I do feel like I have a better intuitive understanding of this repo, so I'm
going to attempt to save it by catching up with it. I already know this is going
to mean wading through a ton of incidental complexity that has resulted from
builds upon builds and assumptions upon assumptions upon assumptions made in the
development process. I have been able to work very quickly. But now I need to
pay the tab. I think the challenge of wading through this repo and reconciling
it to match my own mental model — as well as granting me the authority to do so,
given that I've outsourced a certain degree of my critical faculties to the
agent in developing and designing this — is going to be an instructional,
although painful, experience. And I think it will inform how I design the,
hopefully, intermediary layer of conceptual crossover that I am planning — or
hoping — to resolve this challenge. That is looking like a Vim plugin that
allows for driving by agent as well as operator and restores a pair-programming
ethos to the development process — an ethos that I don't think really properly
survives in chat, when there are prose references to code implementation a step
removed from the architecture itself, and that incentivize the operator to
rubber-stamp approve all agent work and adopt an optimistic, fantastical,
misplaced mental model of where the system exactly is and how it exactly
functions.

This repo is dedicated to trying to ensure and verify agent performance through
deterministic code checks. It's an attempt to add guardrails to a
nondeterministic, unpredictable driver. It's imperfect, but it's a start. But
it's leaky. What I'm starting to wonder is how much do higher-level models,
which behave more predictably and with less guardrails, actually solve the
essential problem of agentic trust. For instance, Opus 5 has had its system
prompt stripped down to 20% of what 4.8 had, and Anthropic is advising that a
large number of skills that were needed before are no longer necessary. The
idea is that the increase in capability by improved models means you need less
steering or guidance — that they can just figure it out through increased
intellectual horsepower. It's telling, though, that the steering and guidance
layers in this case were all natural language. No one is claiming you need less
deterministic code checks. Then again, they're not even talking about that. It
feels more like the product is just "trust the model," and this seems idealistic
at best. The issue I'm getting around to here is that as models get more
capable, the temptation to strip guidance and enforcement increases. The user
becomes more dependent on assuming that the model will do everything 100%
correctly. The problem is that it won't, and the percent that it does not do
correctly — that the user is assuming it is doing correctly — begins the process
of compounding mistakes and mistaken assumptions across the code base, or
whatever written artifact it's working with. You could make an argument that an
increase in the capability of models comes with its own traps and dangers, and
it looks less like Skynet and more like false assumptions and misaligned mental
models by the operator.

This reminds me of what I encountered when deploying agents to do music tour
advancing and logistics. The system I developed was capable but leaky. It was
able to do an incredible amount autonomously, but the things it would miss would
compound and lead to genuine problems. And by problems, I mean logistical and
human-related problems — when I and the system together would misunderstand or
falsely record the state of a set of logistics and needs, and encounter the
harsh reality of when that false record reared its head in the day-to-day
realities of touring. As a result, I was never able to truly offload to the
degree I would have needed to to actually save time at the job. Instead, I had
to use the system but then double-check or verify, while also continuing to
build guardrails into the system — which ended up taking about double the time
it would have taken had I not used the system in the first place.
