# Analysis

Point-in-time evaluations and decision-support write-ups — a question investigated
against evidence (often the live bundle itself), yielding findings and a
recommendation, filed so the reasoning and its conclusion persist. A separate
namespace from `plans` (intended *work* to execute) and `issues` (problems to
track): an analysis is a *reasoned judgment on a question*.

Each analysis is a `type: analysis` doc.

- [Ontology guardrails vs. schema validation for agent loops: what a reasoner buys, and what Coyle's examples actually need](/meta/analysis/ontology-guardrails-vs-schema-validation.md) — evaluates the "Pydantic at the door, ontology at the ledger" pattern against Jido 2 and a custom Elixir layer; finds Jido occupies the door (Action schemas, with `to_tool/0` making the LLM tool schema and the runtime check one declaration) and the effect boundary (Directives defer effects, they don't adjudicate them) but not the ledger, and that a schema decides membership while a logic derives consequences; the sharper findings are that OWL's open-world and no-unique-name semantics *invert* the talk's flagship double-refund catch (a functional property infers `sameAs`, not an error — SHACL's `sh:maxCount` is the formalism that encodes it), that the talk never implements the ledger at all (the code slide is a red placeholder; the working code is Pydantic plus a bare tool-use loop), and that none of its three motivating catches need inference — an enum is a schema, disjointness is a type Elixir expresses better at compile time, once-only is a unique index.
