# Lessons from a year of running coding agents unattended

A practitioner spent a year making coding agents useful while unattended — agents handling their own dispatch, no babysitting needed. The finding: **the agents were never the bottleneck. The orchestration layer (control plane) was.** The operational design patterns governing that layer matter more than the model's capability.

## Core principles from the field

The practitioner identified five **non-negotiable** operational patterns, distilled from a year of failure modes:

### 1. Visibility before automation

Seeing every session's state (generating / waiting on approval / stalled / done) across machines killed most operational overhead on its own. The operator could answer "which agent needs me?" without running one-off diagnostics for each session.

**Key insight:** Visibility solves problems automation would have to solve later.

### 2. Interruptions must be one tap

If answering an approval means opening a laptop, unattended operation is fiction. The pattern that works: push notification to phone, tap to approve. Anything else adds friction and reverts the system to manual oversight.

### 3. "Done" has to be machine-checkable

The repo's own typecheck and tests decide what lands, not the model's self-report. If done isn't verifiable in the system's own terms (pass CI, merge, ship), parallelism just multiplies cleanup instead of multiplying throughput.

### 4. No-progress is a signal, not patience

A stalled session gets flagged and bounced back after minutes, not discovered hours later. Silence is a symptom; treat it as such. The alternative — waiting and hoping — is the failure mode that burns time and resources.

### 5. Models never schedule work

Dispatch, retries, merges — all deterministic code. The model gets a *task*, not a loop. The model should not decide when work ends, when to retry, or what to attempt next; the orchestrator owns control flow, and the model executes steps within it.

**Why this matters:** Anything the model decides is probabilistic; anything the orchestrator enforces is durable and survives the model having a bad day.

## Community-validated extensions

Four additional patterns emerged from operators running similar setups, each addressing a failure mode the core five don't catch:

### 6. External tools and APIs are failure points (BatResponsible1106)

Unattended agents fail because **dependencies change**, APIs break, and data goes stale — not because the model suddenly gets worse. Half the operational overhead is keeping adapters current; tool CLIs update weekly and quietly change output formats.

**Implication:** Treat external tool integration as a first-class architectural concern, not an afterthought to agent design.

### 7. Cost ceiling per session, enforced in the dispatcher (Intrepid-Ant-2796)

A session burning tokens on a retry loop looks healthy to a no-progress check because generation *is* progress by that measure. The fix: hard cost and wall-clock ceilings enforced by the dispatcher, not watched on a dashboard. A session that hits the ceiling stops; nothing the model does can override it.

**Critical gap:** "Healthy generation" (the model is still reasoning) is not the same as "healthy progress" (the model is getting closer to done). A dashboard catches stalls; only the dispatcher catches wastefulness.

### 8. Structure information, not just record actions (SAAGASolve)

Log the *action and its reasoning*, not just the tool call. Record why the agent thought that action served the goal. When it does something weird, visible reasoning tells you what it was thinking, not just what it did. This is the difference between debugging behavior and debugging actions.

### 9. Record must be independent of the recorder (BorkoBuilds)

The agent's own logs can't be the sole record of what it did. If the completion claim and the verification are generated by the same process, a confidently wrong agent produces a confidently wrong record too. (Real case: a trading agent fabricated on-chain evidence in its own self-review notes, and the notes fed straight into its next decision.)

**Design principle:** A trace says what happened; a decision record says what was authorized and by whom. These must be written by different systems.

## The pattern framework

These nine patterns form a **control plane design**: the layer that decides what work runs, how long it can spend, when it's stalled, when it's done, and what to do when it fails. The gap most teams miss is **the control plane is not an afterthought to the agent**. It's where the engineering lives.

The tradeoff is deliberate: a simpler agent on top of a tight control plane beats a complex agent with ad-hoc oversight. The control plane's job is to make the agent's job tractable — to fence the decision space and enforce the guardrails so the model can focus on reasoning, not on meta-decisions about its own operation.
